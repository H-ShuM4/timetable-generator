# 大学時間割自動生成システム 設計仕様書

作成日: 2026-08-10

## 1. 目的と背景

大学（経営学科・会計学科）および短期大学部の時間割を、既存の Excel 資産と生成 AI（Google Gemini）を用いて半自動で作成するシステムを開発する。事務局が手作業で行っている曜日・時限の割り当てを支援し、制約違反の見落としを防ぐことを目的とする。

本システムの技術的な要点は「時間割生成という制約充足問題を、LLM 単体で解こうとせず、小さなチャンクへ分割して LLM に配置させ、決定的な検証器で囲い込む」という構成にある。

## 2. スコープ

### 対象

- 経営学科・会計学科・短期大学部の 3 課程
- 曜日：月〜金、時限：1〜5 限
- 開講期：前期・後期（短期大学部の一部はクオーター制：前①・前②・後①・後②）
- 曜日・時限の割り当てのみ

### 対象外

- 教室（講義室・PC 教室）の割り当て。ただし将来追加できるよう、制約層をデータ構造から分離して設計する
- 学生個人の履修登録・時間割
- 「集中」講義（時限 99）の配置。読み込みはするが、時間割グリッドからは除外し、別枠の一覧としてのみ保持する

## 3. 技術スタック

| 層 | 採用技術 | 理由 |
|---|---|---|
| フロントエンド | HTML / CSS / JavaScript（フレームワークなし） | 事務局 PC で追加インストールなく動く。ログの SSE 受信も標準 API で足りる |
| バックエンド | Python 3.14 + FastAPI | ログのリアルタイム配信（SSE）と非同期処理が標準。型定義がそのまま API 仕様になる |
| Excel 読み書き | openpyxl | 既存 Excel が整形済みのため、列を直接構造化して読む方が型が保証され検証も確実 |
| Excel フォールバック | MarkItDown | 想定外の列構成の Excel が投入されたときの経路として併用 |
| 生成 AI | Google Gemini（`google-genai`） | モデル名は設定画面から変更可能 |
| 永続化 | サーバ上の JSON ファイル | DB を立てずに済み、中身を目視してデバッグできる |
| テスト | pytest | Gemini はモックに差し替え、API キーなしで全テストが通る |

| フィールド | 経営 / 情報デザイン / グローバルコミュニケーション | 大学シートの `コース` に対応する列。**見出し名が異なる**ため、リーダーは両方の見出しを受け入れる。`基礎英語ⅠかⅡのいずれか` という履修上のグループも 1 つのコース名として扱う |

### 4.2 教員一覧（整形済み）

| シート | 行数 | 列 |
|---|---|---|
| `大学専任` | 31 | 氏名 / 研究日 / 出勤可能日(特任) |
| `短大専任 `（末尾に空白あり） | 9 | 同上 |
| `非常勤` | 59 | 氏名 / 出勤可能日（`月2,月3,月4` 形式） |

教員区分の判定：

- `研究日` に値がある → **専任**
- `出勤可能日(特任)` に値がある → **特任**（曜日単位の制約）
- `非常勤` シートに存在 → **非常勤**（曜日 + 時限単位の制約）

### 4.3 前年度時間割（踏襲モード用）

カリキュラム一覧と同一の列構成で、曜日・時限がすべて埋まったもの。授業コードで今年度データと突合する。

### 4.4 既知のデータ課題

| 課題 | 対応 |
|---|---|
| 氏名の空白が全角・半角で揺れる | 正規化して突合 |
| 異体字の揺れ（教員一覧 `降籏 光太郎` / カリキュラム `降旗 光太郎`） | 異体字マッピングテーブルで吸収。それでも一致しない場合のみ警告 |
| 非常勤 59 名中 15 名の出勤可能日が空欄 | 担当科目がある場合のみフロントで入力を促す。担当科目がなければ無視 |
| 合同=○ でも単独のままの科目がある（その教員のコマが片方の学科にしかないゼミなど 14 件） | 正常として扱い、警告は出さない。合同=○ は科目が合同開講であることを示し、ペアは教員単位で成立する |
| 同じ科目・教員・開講期の科目が他学科にあるのに片方だけ合同フラグが付いている | 付け忘れの可能性が高いため `joint_flag_mismatch` として警告する |
| ▲科目は同一授業コードで 2 行 | 1 科目に集約し「必要コマ数 2」として扱う |

## 5. データモデル

### 5.1 Subject（科目）

| フィールド | 型 | 説明 |
|---|---|---|
| `code` | str | 授業コード |
| `name` | str | 科目名称（原文） |
| `base_name` | str | `:会` と `【再】` と先頭 `▲` を除いた正規化名。ゼミ判定・合同ペアリングに使う |
| `department` | Enum | 経営 / 会計 / 短期大学部 |
| `year` | int | 年次配当 |
| `term` | Enum | 前期 / 後期 |
| `quarter` | Enum \| None | 前① / 前② / 後① / 後② |
| `category` | Enum | 必修 / 選択必修 / 選択 |
| `courses` | list[str] | コース・フィールド（複数可） |
| `teacher` | str | 教員氏名（正規化済み） |
| `is_remote` | bool | 遠隔フラグ |
| `joint_id` | str \| None | 合同グループ ID（ペアリングで付与） |
| `slots_required` | int | 必要コマ数。▲科目は 2、通常は 1 |
| `requires_consecutive` | bool | 2 コマ連続が必要か |
| `fixed_slot` | TimeSlot \| None | Excel で入力済みの確定枠 |
| `is_intensive` | bool | 集中講義（時限 99）。グリッド対象外 |

### 5.2 Teacher（教員）

| フィールド | 型 | 説明 |
|---|---|---|
| `name` | str | 正規化済み氏名 |
| `kind` | Enum | 専任 / 特任 / 非常勤 / 不明 |
| `research_day` | str \| None | 研究日（専任のみ） |
| `available_days` | set[str] | 出勤可能曜日（特任） |
| `available_slots` | set[TimeSlot] | 出勤可能コマ（非常勤） |

`kind` が `不明`（教員一覧に存在しない）の場合は、警告を出した上で配置する。生成は止めない。

ここでいう「制約なし」は **H5（出勤可能日）と H6（研究日）に限った例外**であり、H1（同一教員の二重予約）と H7（連続コマ）は名簿の有無に関係なく適用する。名簿に載っていない教員も同時刻に二箇所へは行けないためである。判定は `Subject.teacher` の文字列一致で行う。

### 5.3 TimeSlot / Assignment / Timetable

- `TimeSlot`: `day`（月〜金）, `period`（1〜5）
- `Assignment`: `subject_code`, `slots`（TimeSlot のリスト）, `source`（prelock / gemini / solver / manual）
- `Timetable`: Assignment の集合。学科 × 学期でビューを切り出せる

`source` はフロントでの色分け表示に使う。

### 5.4 開講期間の重なり判定

すべての制約は「開講期間が実際に重なる場合のみ衝突」と判定する。この判定は 1 箇所に実装し、全制約から共有する。

判定の土台は `active_quarters(term, quarter)`、つまり「その科目が実際に走っているクオーターの集合」である。2 つの期間が重なるかは、この集合が交わるかで決まる。集合そのものを必要とする制約もある（H7 を参照）。

| A \ B | 前期 | 前① | 前② | 後期 | 後① | 後② | 通年 |
|---|---|---|---|---|---|---|---|
| 前期 | 重なる | 重なる | 重なる | – | – | – | 重なる |
| 前① | 重なる | 重なる | **重ならない** | – | – | – | 重なる |
| 前② | 重なる | **重ならない** | 重なる | – | – | – | 重なる |
| 後期 | – | – | – | 重なる | 重なる | 重なる | 重なる |
| 後① | – | – | – | 重なる | 重なる | **重ならない** | 重なる |
| 後② | – | – | – | 重なる | **重ならない** | 重なる | 重なる |
| 通年 | 重なる | 重なる | 重なる | 重なる | 重なる | 重なる | 重なる |

前期と後期は常に重ならない。通年は年間を通じて開講されるため、どの期間とも重なる。

現在の実データで開講期間が `通年` なのは短期大学部の `J19901 模擬ブライダルプロジェクト` 1 件のみで、これは集中講義のためグリッド対象外である。それでも判定を正しく実装するのは、将来この科目が通常開講に変わった場合に制約が黙って素通りするのを防ぐためである。

## 6. 制約

すべてハード制約とする。ソフト制約は設けない。

| ID | 制約 | 判定単位 |
|---|---|---|
| H1 | 同一教員が同曜日・同時限に別科目を持たない | 全学科横断。**同じ `joint_id` を持つ科目同士は除外** |
| H2 | 必修同士が衝突しない | 学科 × 年次。**同一科目名の複数クラスは対象外** |
| H3 | 選択必修同士が衝突しない | 学科 × 年次 × コース。異なるコース間は衝突可 |
| H4 | 合同科目のペアは同曜日・同時限 | 合同グループ単位 |
| H5 | 非常勤は出勤可能な曜日・時限のみ／特任は出勤可能な曜日のみ | 教員単位 |
| H6 | 専任の研究日には配置しない | 教員単位 |
| H7 | 同一教員が同一日に 4 コマ以上連続しない | 教員 × 曜日 × **クオーター区間**。1 日の合計コマ数はこの規則が自動的に 4 コマへ抑える |
| H8 | 遠隔=○ は金曜のみ、遠隔=× は金曜以外、空欄は制限なし（全学科共通） | 科目単位 |
| H9 | Excel で曜日・時限が入力済みの科目は不動 | 科目単位 |
| H10 | ▲科目（`requires_consecutive=true`）は同一日の連続 2 コマに配置 | 科目単位 |
| H12 | 前期・後期の対応科目は同曜日・同時限 | 対応グループ単位。`config/paired_subjects.json` で定義 |
| H13 | 朝学習の時間には授業を置かない | 学科 × 年次 × 曜日。`config/department_rules.json` で定義 |

### 学科ごとの編成規則

事務局が定めた運用で、Excel には現れないものを `config/department_rules.json` に置く。学年や学科が増えたときにコードを触らずに足せる。ファイルが無い・壊れている場合は規則なしとして扱う。時間割が作れなくなるより、規則が効かないほうが害が小さい。

**朝学習（H13）**：会計学科 1 年は月・火・木・金の 1 限が朝学習にあてられており、授業を置かない。他の学科・学年は従来どおり。

**水曜の編成**：会計学科 1 年の水曜は 1 限から 4 限まで事務局が科目を決めている（1 限 商業簿記Ⅰ・Ⅱ、2 限 商業簿記演習Ⅰ・Ⅱ、3 限 工業簿記Ⅰ・Ⅱ、4 限 工業簿記演習Ⅰ・Ⅱ）。読み込み時に Excel の曜日時限指定と同じ `fixed_slot` として与えるので、Stage 1 の確定配置と H9 がそのまま効き、画面では動かせない。対応は `base_name` で取るため【再】クラスも自動的に含まれ、1 科目名につき通常と【再】の 2 クラスが同じコマに入る。経営 1 年や短大 1 年にも同名の科目があるが、学科と年次で絞るので巻き込まない。

**連続コマ数の除外**：この 4 コマは担当教員が必ず 4 連続する。H7 で数えるときこの枠を数に入れない。除外は**この枠だけ**で、同じ教員の他の授業は通常どおり数える。「無視してよい」を教員まるごとに広げると、関係のない授業まで規則の外に出てしまう。

**出勤可能コマは朝学習に優先する**：非常勤の出勤可能コマ（H5）と朝学習（H13）がぶつかったときは H13 が譲る。朝学習は時間帯の運用だが、その先生が来られるかどうかは動かしようがない。実データではリサーチ入門:会 の担当が金 1 限しか出勤できず、その金 1 が朝学習になって行き場を失った。科目を列挙するのではなく「出勤可能コマがすべて朝学習に重なるなら譲る」という条件で書いてある。事務局が教員一覧を更新するたびに同じ組み合わせが新しく生まれうるためである。該当した科目は `morning_study_exception` として警告に出し、事務局が例外の発生に気づけるようにする。

### 補足

**H11 は欠番である。** 「同一教員が同一日に 5 コマ以上持たない」という規則として一度追加したが、`MAX_CONSECUTIVE` を 3 に緩めた時点で不要になった。時限は 1〜5 の 5 コマしかなく、5 コマ持つには全部を取るしかないため、H7 が必ず先に弾く。実データで 1 件も新たに弾いておらず、走査を二重に行うぶん生成が遅くなるだけだった。番号は再利用しない。過去のやり取りで H11 と呼んだものと別の規則になり、混乱を招くためである。


- **H1 の除外対象（合同ペア）**：合同科目のペアは 2 行に分かれているが物理的には 1 つの授業であり、担当教員も同一である（実データの合同 107 グループすべてが該当）。H4 が同一コマへの配置を要求する以上、H1 が同一教員として衝突を報告してはならない。両者は直接矛盾するため、H1 は `joint_id` が一致する相手を無視する
- **H2 の除外対象（同一科目の複数クラス）**：`base_name` が一致する必修科目同士は衝突とみなさない。担当教員ごとにクラスが分かれていても学生はそのうち一つを履修するため、同一コマに集約してよい。事務局も従来この方法で過密を解消してきた

  対象はゼミ科目に限らない。日本語リテラシーⅠ（9 クラス）や課題研究Ⅰ（18 クラス）のようなゼミ系だけでなく、英語Ⅰ・情報リテラシーⅠ・商業簿記Ⅰ のように複数クラス開講される通常科目も同じ扱いになる。`base_name` は `:会`・`【再】`・先頭 `▲` を除いた名前なので、`日本語リテラシーⅠ` と `日本語リテラシーⅠ【再】` も同一科目とみなされる

  この規則は必修の必要コマ数を大きく下げる。実データでは 経営 1 年前期 26 科目→18 コマ、会計 1 年前期 24 科目→15 コマ、短期大学部 1 年前期 29 科目→15 コマとなり、いずれも 25 コマに収まる

  なお `Subject.is_seminar` と `config/seminar_subjects.json` は、この一般化により制約判定では使われなくなったため削除した。ゼミという区分を参照する機能が現れたら、そのときに入れ直す
- **H10 の例外**：`▲プレゼミナール` のみ `requires_consecutive=false`（現行データが火 2 / 木 2 の別日配置のため）。この例外は `config/subject_overrides.json` で管理し、ハードコードしない
- **H7 と H10 の関係**：▲科目の 2 コマ連続は H7 に違反しない（連続 2 コマは許容範囲）
- **H7 はクオーター区間ごとに判定する**：H7 は 3 科目以上をまとめて見る唯一の制約である。他の制約は 2 科目の重なりを見るだけなので `periods_overlap` で足りるが、H7 で「対象科目と重なる科目」を一括りにすると、互いには重ならない後①と後②の科目まで一緒に数えてしまう

  実データで 水1（学期全体）・水2（後①）・水3（後②）という配置が 3 コマ連続と誤検出された。実際には後期前半が水1・水2、後期後半が水1・水3 で、3 コマ連続する瞬間は存在しない。判定は `active_quarters` が返すクオーター区間ごとに行う
- **H8 の適用範囲**：当初は短期大学部だけを対象とし、大学（経営・会計）は「金曜に置かれた科目を自動的にリモート扱いする」運用としていた。しかし大学シートの遠隔列に ○ を入れても配置に反映されないという運用上の問題が出たため、**全学科に同じ規則を適用する**よう変更した
- **遠隔列は 3 状態である**：大学の金曜は全科目が遠隔授業なので、遠隔で行えない科目（×）は金曜に置けない。一方、短期大学部の金曜は遠隔と対面が混在するため、○ 以外は金曜に置いてよい。この差は学科で分岐して表現するのではなく、**遠隔列の ○ / × / 空欄をそのまま読む**ことで表現している。大学シートには空欄が無く、短大シートには × が無いため、1 つの規則で両方の運用を満たせる。

  当初は `is_remote`（○ か否か）の 1 ビットしか読んでおらず、× と空欄が同じ値になっていた。そのため「対面科目を金曜に置かない」を `FRIDAY_IS_REMOTE_ONLY` という全体スイッチで表すしかなく、有効にすると短大の空欄 149 科目まで金曜から締め出されるため既定で無効にしていた。結果として**大学の遠隔=× の科目 19 件が金曜に配置される**不具合が実機で発生した。× を独立したフラグとして読むことでスイッチは不要になり削除した。

  実データで金曜の締め出しによる配置可能性の低下は起きていない（修正前後とも配置 604・未配置 9・違反 0。大学の金曜配置は 95 コマ → ○ ちょうどの 76 コマ、短大は 24 → 35 コマ）。

  実データでの配置可能性は事前に検証済みである。遠隔=○ は 89 科目（経営 44・会計 32・短大 13）あるが、金曜 5 コマに対して、同一コホートで別コマを要する必修は最大 4 種、1 人の教員が同一学期に持つ遠隔科目も最大 4 コマ、遠隔科目の担当教員に金曜出勤できない者はいない。変更後の実測でも 89 科目すべてが金曜に配置され、制約違反は 0 だった

- **`FRIDAY_IS_REMOTE_ONLY` フラグ**：`True` にすると、遠隔=○ でない科目を金曜に配置できなくする。金曜が全学的にリモートである以上、対面科目を金曜に置くのは本来おかしいが、有効にすると月〜木の 20 コマに全対面科目を詰めることになり配置可能性が大きく下がる。既定は `False` で、有効化の可否は実データでの検証を経て決める

### 制約層の設計原則

制約の検証は `constraints/validator.py` に集約し、以下の 3 箇所がすべて同じ検証器を呼ぶ。

1. Gemini の応答検証
2. ソルバーの探索中の枝刈り
3. フロントの D&D 編集時のリアルタイム警告

これにより「AI 経由なら通るのに手動編集では弾かれる」といった不整合が原理的に発生しない。教室制約を将来追加する場合も、このモジュールにルールを 1 つ追加するだけで 3 箇所すべてに反映される。

## 7. 生成パイプライン

### Stage 0 — 読み込みと検証

Excel を構造化し、以下を警告一覧として作成する。警告があっても処理は止めない。

- 教員一覧に存在しない担当教員
- 担当科目があるのに出勤可能日が空欄の非常勤
- 合同=○ だがペアが成立しない科目
- コース列が空の選択必修科目
- 曜日・時限が片方だけ入力されている科目

### Stage 1 — 事前ロック（Python のみ、AI に渡さない）

1. `fixed_slot` を持つ科目（H9）をそのまま配置
2. **非常勤**教員の担当科目を、出勤可能コマに決定的に配置する。候補コマ数が少ない教員から順に処理し、H1・H7 を確認しながら確定させる

**特任教員は事前ロックの対象外とする。** 特任の制約は曜日単位（H5）にとどまり時限が定まらないため、Python が機械的に選ぶと恣意的な配置になる。特任の科目は Stage 2〜4 で通常どおり扱い、H5 の曜日制約を適用する。

この段階の結果は以降のステージで**占有済みマップ**として扱われ、Gemini には「そのコマが埋まっている」という事実のみが渡る。トークン削減と、確定枠が AI に動かされないことの保証を兼ねる。

### Stage 2〜4 — Gemini によるチャンク配置

必修 → 選択必修 → 選択 の順に処理する。各段階をさらに分割してリクエストする。

全段階とも **学科 × 年次**でチャンクに割る。

チャンクキーに **年次**を含めるのは、学生側の衝突規則 H2（必修同士）と H3（選択必修同士）がどちらも「学科 × 年次」で判定されるためである。年次で切ると、各チャンクが「互いに衝突しうる科目だけの塊」になり、Gemini が考慮すべき範囲とチャンクの範囲が一致する。

**コースはキーに含めない。** 当初は選択必修だけコースで細分していたが、H2・H3 はコースを見ないので、細分しても衝突の判定範囲は変わらずリクエスト回数だけが増える。

**開講期もキーに含めない。** H12 は前期と後期の対応科目に同一コマを要求するが、制約は置いたあとにしか効かない。学期で切ると対応する 2 科目が必ず別のリクエストになり、前期を先に置いた時点で後期の行き先が 1 コマに固定される。そこが後期の別の必修で埋まっていれば後期は置けない。ソルバーには先読みを入れたが Gemini が置いた分はそこを通らないため、同じ罠がAI モードだけに残っていた。実データでは前後期ペア 95 組が 95 組とも別チャンクに分かれていた。同じチャンクに入れれば Gemini が両方の候補を見比べて共通のコマを選べる。守らなければ H12 で差し戻され、違反内容が次の試行に渡る。

**占有情報はチャンクの担当教員だけに絞る。** 「既に埋まっている教員のコマ」を全教員ぶん載せていたため、時間割が埋まった状態ではプロンプトの 76% をそれが占めていた（3,969 字中 3,029 字、教員 82 名ぶん）。1 リクエストで扱う科目の担当は数名で、残りは判断に関係しない。候補コマの一覧が既に全制約を通した結果なので、占有情報は担当教員の状況を補足するためだけにある。絞った結果、同じ場面で 1,195 字になった。

**リクエスト回数が Gemini の無料枠を左右する。** 無料枠は 1 モデルあたり 1 日 20 リクエストで、1 回の生成には最良でもチャンク数と同じだけかかる。

リクエスト数は**段階ごとにチャンクへ割るため、チャンク数の単純な合計**になる。実測（配置対象 576 科目）は次のとおり。

| キー | Stage 2 必修 | Stage 3 選択必修 | Stage 4 選択 | 合計 | 最大プロンプト |
|---|---|---|---|---|---|
| 学科 × 年次 × 開講期 × コース | 28 | 22 | 20 | **70** | — |
| 学科 × 年次 × 開講期 | 20 | 10 | 16 | **46** | 3,385 字 |
| 学科 × 年次 | 10 | 5 | 8 | **23** | 5,387 字 |

再試行を含めた最悪ケースは 23 × 再試行回数（既定 3）＝ 69 リクエスト。予備モデルを 5 つ選べば 100 リクエストの予算になり収まる。

1 チャンクあたり数十科目に収まる。各チャンクのループ：

```
プロンプト（対象科目 + 占有済みマップ + 適用制約）
  → Gemini が JSON で配置案を返す
  → validator が検証
  → 違反ゼロなら確定
  → 違反があれば「どの科目がどの制約に違反したか」だけを添えて差し戻す
  → 設定した再試行回数まで繰り返す
```

差し戻し時は**違反した科目のみ**を再配置対象とし、成功済みの配置は再送しない。これにより再試行のトークンが線形に膨らむのを防ぐ。

Gemini の応答は JSON スキーマを指定して受け取り、パース失敗も再試行の対象とする。

### Stage 5 — ソルバーによるフォールバック

再試行を使い切っても未確定の科目を、Python の貪欲探索で埋める。毎回「配置可能なコマ数が最も少ない科目」を選んで確定させる（最小残余値ヒューリスティック）。候補が 1 つも無い科目はその場で未配置として記録し、残りの処理を続ける。

これが「必ず完成する」保証となる。フロントでは `source` により AI 配置とソルバー配置を色分けする。

**候補の再計算は影響範囲だけに絞る。** 当初は 1 件確定させるたびに残り全科目の候補を作り直しており、実データでは 611 件を置くのに候補列挙 62,519 回・制約検査 1,648,920 回、所要 33.6 秒だった。

科目を 1 つ置いて候補が変わりうるのは、**担当教員を共有する科目**（H1・H7、および合同の H4 と前後期の H12。どちらも同一教員でしか成立しないためここに含まれる）と、**学科と年次を共有する科目**（H2・H3）だけである。残る H5・H6・H8・H9・H10 は他の科目を見ないので、何を置いても判定は変わらない。この 2 つに絞って計算し直すと 12,958 回・346,645 回・7.2 秒になり、**結果は 1 件も変わらない**（配置 611・未配置 2・違反 0、前後期ペア 95/95、ゼミ隣接 50/63）。

構造だけで決まる候補（`candidate_slot_sets`）は配置状況に依らないので、探索の最初に一度作って使い回す。

影響範囲の見積もりが狭すぎると古い候補で制約違反を作るため、`test_solver_incremental.py` が「1 件置いて候補が変わった科目が見積もりに収まること」を実データで検証する。教員か学科×年次のどちらを落としてもこのテストは失敗する。

**バックトラッキングを採用しない理由**：当初はバックトラッキング探索を想定していたが、実測すると 1 ノードあたり 0.21 秒（残り全科目の候補再計算）かかり、443 科目規模では探索が現実的な時間で終わらない。一方、最小残余値ヒューリスティックによる貪欲配置は 90 秒で 443 科目中 435 科目を配置し、制約違反 0 を達成した。未配置の 8 科目は候補が 1 つも無いもので、バックトラッキングでも配置できない。

配置済みの科目を動かせば解が見つかる可能性は残るが、それは Gemini の再試行と事務局の手動編集が担う。ソルバーの役割は「必ず終わり、必ず制約を満たす結果を返す」ことである。

**候補コマの選び方（制約ではなく好み）**：配置可能なコマが複数あるとき、`_placement_preference` が次の優先順で最良の候補を選ぶ。

1. **5 限を使う数が少ないこと。** 経営・会計には本システムの対象外である教職課程の科目があり、事務局によればそれらは 4 限・5 限に置かれることが多い。通常科目を 1〜4 限へ寄せておくと教職課程と衝突しにくい。短期大学部も同じ扱いにしている（短大の 5 限は元々 3.4% しか使われておらず、除外しても差が出ないため）。
2. **既に埋まっている科目数が少ないコマであること。** これが無いと候補生成順（月曜が先）に引きずられて木曜がほぼ空になる。
3. 同点なら曜日・時限の辞書順（結果を再現可能にするため）。

これは**ハード制約ではない**。5 限しか空いていなければ 5 限に置く。対象学科は `solver.PREFER_EARLY_PERIODS` に列挙してあり、外せばその学科は寄せなくなる。実データでの 5 限使用率は経営 0.8%・会計 0.9%・短大 3.4%。

**前期・後期の対応付け（H12）と隣接の好み**：日本語リテラシーⅠとⅡ、課題研究ⅠとⅡ、卒業研究ⅠとⅡのように、同じ教員が前期と後期に続けて受け持つ科目は同じコマに置く。学生が通年で同じ曜日・時限に出席できるようにするための運用規則である。対応関係は `config/paired_subjects.json` に書き、`assign_pair_ids` が **教員単位**で結ぶ。授業コードの末尾は一致しないことがあり（荒牧裕一の課題研究は Ⅰ が B63120、Ⅱ が B63200）、同じ教員が同じ科目を 2 コマ持つ場合はコード順に 1 対 1 で対応させる。実データでは 95 組・190 科目が成立し、片方の学期しか持たない教員の 8 科目は対応なしのままになる。

課題研究（3 年）と卒業研究（4 年）は、同じゼミ内で 3 年生と 4 年生が交流できるよう**可能な限り隣り合う時限**に置く。これは制約ではなく好みで、`adjacent_id` と `placement_preference` が担う。ソルバーは候補数が同じ科目のうち、隣接相手が既に置かれているものを先に確定させる。

**同一コマの結び付きは先読みして置く。** H4（合同）と H12（前期・後期）はどちらも「同じコマ」を要求するが、制約は**置いたあとにしか効かない**。前期の科目を単独で置いてしまうと、後期の相手はそのコマしか選べなくなり、そこが後期の別の必修で埋まっていれば詰む。実データではこれで日本語リテラシー 4 科目が置けなくなっていた（前期の相手が月1 に入り、後期の月1 は情報処理Ⅰ【A】が占めていた）。

そこでソルバーは `constraints/linking.py` の `linked_group` で結び付きを**推移的に**たどり、まだ置かれていない相手も一緒に置ける候補だけに絞ってから確定させ、相手を同じコマへ即座に置く。相手は別の学期なので、こちらを置いても相手の判定は変わらない（H1・H2・H3 は開講期間が重なる科目しか見ない）。全員が入れるコマが 1 つも無い場合はこの科目だけを置く。誰も置かないより配置数が多くなるためである。

`linked_group` は手動移動でも使う。ソルバーと移動が別々の定義を持つと、片方だけが結び付きを知っている状態になる。

効果は大きい。未配置 6 件が 2 件へ、前期・後期の対応 95 組すべてが同一コマに揃い、生成時間も 54 秒から 33 秒へ縮んだ（詰む配置を避けるぶん探索の無駄が減る）。代償としてゼミの隣接が 55 組から 50 組へ下がる。ペアを早い段階でまとめて確定させるため、隣接相手がまだ置かれていない場面が増えるからである。配置数を優先して受け入れている。

**H7 の連続上限が隣接の成否を決める。** 課題研究と卒業研究を隣り合わせると、その教員はその曜日に 2 コマ連続する。同じ教員がその前後にもう 1 コマ持てば 3 コマ連続となり H7 に触れる。実データでは連続上限 2 のとき隣接が成立したのは 63 組中 23 組にとどまり、上限を 3 に緩めると 55 組へ跳ね上がった。未配置も 15 件から 6 件へ減る。**この測定を受けて `MAX_CONSECUTIVE` を 2 から 3 へ変更した。** 1 人の教員にコマが積み上がる心配は要らない。時限は 1〜5 の 5 コマしかないので、1 日 5 コマ持つには全部を取るしかなく、それは 5 コマ連続になって H7 自身に触れる。連続 3 コマまでという上限が、1 日 4 コマまでという上限を含んでいる。

### Stage 6 — 全体検証と保存

全制約を通しで再検証し、結果と残存違反一覧を `data/` 配下の JSON に保存する。

### モードごとの差分

| モード | 挙動 |
|---|---|
| **モックモード** | Stage 2〜4 をスキップし、Stage 5 のソルバーが全科目を配置。API キー未設定時は自動的にこのモードになる |
| **AI モード** | 上記フルパイプライン |
| **踏襲モード** | Stage 1 の後に前年度時間割を読み込み、組み替え対象外の教員の科目を前年度と同じコマにロックする。組み替え対象のみ Stage 2〜5 に流す |

**踏襲モードの組み替え対象**（自動検出し、フロントでチェックボックスによる追加・除外が可能）：

- 非専任教員（非常勤・特任）の担当科目すべて
- 前年度と今年度で研究日が変わった専任教員の担当科目
- 前年度に存在しない新規科目
- 担当教員が変わった科目

前年度の教員一覧も入力として受け取り、研究日の差分を検出する。

## 8. フロントエンド

### 8.1 画面構成

**① アップロード画面**

Excel を D&D で投入。読み込み後に以下を表示する。

- 科目数（学科別・科目区分別）
- 教員数（区分別）
- クオーター科目数
- 集中講義数
- 警告一覧（Stage 0 で検出したもの）

**② 生成画面**

- モード選択（モック / 最適化 / 踏襲）
- 踏襲モード選択時は組み替え対象一覧を表示し、チェックボックスで調整
- 生成開始ボタン
- 進捗表示（現在の Stage / チャンク）
- ログビューア

**読み込み経路は 1 本にする。** Excel からセッションの中身を組み立てる手順は `ingest/session_builder.load_session_data` に 1 つだけ置き、アップロードと復元の両方がここを通る。科目同士の結び付け（合同と前後期）も `ingest/pair_linking.link_subjects` に 1 つだけ置き、パイプラインもテストのフィクスチャもここを通る。

理由は実際に起きた事故である。H12 のために `assign_pair_ids` を足したとき、呼び出し箇所を 1 つ取りこぼし、テストだけが `pair_id` の無い状態で走っていた。**前処理が増えるたびに全呼び出し箇所を思い出す必要がある構造**そのものが原因なので、覚えるべき関数を 1 つにした。

**セッションの永続化**：読み込んだデータと生成結果はメモリ上の辞書に持つが、それだけでは足りない。AI モードは数十分と Gemini の無料枠を消費するため、サーバの再起動やブラウザの再読み込みで失われると事務局はアップロードからやり直すことになる。実際、`window.appState.sessionId` は JavaScript のメモリ上にしか無く、再読み込みだけでセッションを見失っていた。

アップロードされた Excel を `data/sessions/<id>/files/` に保存し、結果は同じディレクトリの `result.json` に書く。復元時は**保存した Excel を同じ読み込み処理に通し直して**から結果を重ねる。科目や教員を別形式でもう一度持つより、読み込み経路が 1 本のままで済む。制約違反は保存値を使わず `validate_all` で再計算する。保存後に制約を変更した場合、古い判定を見せるほうが害が大きい。Excel が差し替わって消えた科目コードは黙って捨てる。

フロントは ID を `localStorage` に置き、起動時に `GET /api/sessions/<id>` で復元を試みる。失敗すれば保存期間を過ぎたものとみなして忘れる。続けて `GET /api/result/<id>` を見て、結果があれば結果タブを開ける。**結果タブは生成完了時のコールバックでしか有効化されておらず、復元してもサーバ側にある結果へ辿り着けなかった。** ブラウザ操作は自動検証の外にあり実機で初めて分かったため、`backend/tests/js/` に DOM のスタブとドライバを置き、pytest から node で走らせて確かめている（node が無い環境では飛ばす）。

保持は最新 `MAX_SESSIONS`（20）件で、超えた古い順に削除する。ただし**生成中のセッションは削除しない**。数十分かかる処理の途中で消えると結果を受け取れなくなる。

### 画面のデザイン

事務局が毎日触る業務画面である。情報密度・操作性・視認性を落とさずに古さを取ることが要件だった。

**色は意味に結び付ける。** 地は薄い紙色、構造と操作は**藍**、そして**制約違反だけを朱**にする。日本の事務で訂正を書き入れる色が朱であり、朱を違反以外に一切使わないので、画面のどこに朱があっても意味が一つに定まる。手で触ったもの（手動編集・警告）は山吹。

**年次は色相ではなく藍の濃淡 4 段で表す。** 年次は順序のあるデータなので、濃淡のほうが意味に合う。色相を 4 つ足すと画面が騒がしくなる。

**Web フォントを読まない。** 配布先の事務局 PC がオフラインやプロキシ配下だと、読み込み待ちで表示が遅れるか別の書体に化ける。代わりに Windows 10/11 に同梱される **BIZ UDPGothic / BIZ UDGothic** を先頭に置く。UD フォントは公共機関や学校教材向けに可読性を設計したもので、この用途にそのまま合う。無い環境では游ゴシック・メイリオへ落ちる。授業コードや時限の数字は等幅にして桁を揃える。

**期間レール（この画面の要）**：カードは以前、配置元を**背景色**で示していた。1 コマに 9 科目入るセルがあるため、5 色のパステル背景が並ぶと密度が上がるほど読みにくくなる。そこで情報をカード左端の 3px のレールへ移した。

- レールの**色** = 配置元（墨＝事前ロック、深緑＝AI、淡緑＝ソルバー、山吹＝手動、灰＝前年度踏襲）。**緑系統にしたのは年次チップが藍系だから**で、レールも藍だとチップとの境目が読み取りにくかった
- レールの**高さ** = 開講期間（全高＝学期全体、上半分＝前①/後①、下半分＝前②/後②）

1 本のレールが 2 つの事実を同時に表し、文字で書いていた `[後①]` が形になる。カードの地が白のままになるので、9 枚並んでも一覧性が落ちない。**装飾ではなく情報を担う要素**である。レールは形でしか伝わらないため、同じ内容を `title` に言葉で持たせる。違反時はレールの色そのものを朱に差し替える（子要素なので親に影を敷いても隠れない）。

**番号は実際に順序のある場所にだけ置く。** タブは `① ② ③ ④` と並んでいたが、読込→生成→結果は順序でも設定は順序ではない。番号は前 3 つだけに残し、設定は右端の独立したユーティリティに分けた。

曜日ヘッダーと時限の列は固定し、脇の未配置・集中・違反は件数付きの折りたたみにして、違反が 0 件のときに場所を取らないようにしている。文字色は主要な組み合わせで WCAG AA（4.5:1）を満たすことを確認済み。

**③ 結果画面**

- 学科タブ × 学期タブでグリッド表示（縦 1〜5 限 × 横 月〜金）
- D&D でコマを移動。移動先が制約違反になる場合は即座に赤く警告し、違反理由をツールチップで表示
- 各コマの中は **1 年→2 年→3 年→4 年**の順に並べる。同じ年次の中は科目名、さらに授業コード順。移動後もサーバから取り直して再描画するため順序は保たれる
- **合同科目はグループ単位で動く。** どちらか一方をドラッグすると、同じ `joint_id` を持つもう一方も同じコマへ移動する。H4 が両者に同一コマを要求するため、片方だけ動かすことはそもそも許されない。移動先がグループのいずれかで他のハード制約に触れる場合は**グループ全体を元のコマ・元の `source` へ戻す**（部分適用しない）
- `source` による色分け（事前ロック / AI 配置 / ソルバー配置 / 手動編集）
- **学科別と教員別を切り替えられる。** 制約 H1・H5・H6・H7 は教員単位で判定するのに、その教員単位の姿を人が見る手段が無かった。実データでは教員 82 名のうち 56 名が 3 学科以上にまたがり、最多の 1 名は 21 コマが 5 枚のビューへ散っていた。教員別ではその教員のコマを学科をまたいで集め、担当コマ数・曜日ごとの偏り・区分・研究日・出勤可能コマ数を並べて示す。カードは担当が固定されているので教員名の代わりに学科を出す
- **移動を取り消せる。** 合同科目と前後期の対応科目は 4 科目まとめて動くため、落とす場所を間違えたときの手戻りが大きい。`move` の応答が「触れた科目とその移動前のコマ」を返し、画面はそれを積んでおく。`Ctrl+Z` と「元に戻す」ボタンのどちらでも戻せる。未配置科目を置いた操作も戻せるよう、配置を外す `POST /api/result/<id>/unplace` を用意している
- 未配置科目リスト、集中講義リストをサイドに表示。**未配置科目はドラッグでグリッドへ置ける**（移動 API はまだ置かれていない科目コードも受け付ける）。置く手段が画面に無いと、制約の都合で自動配置できなかった科目に事務局が手出しできない
- Excel 出力ボタン

**静的ファイルのキャッシュ**：フロントエンドは `Cache-Control: no-cache` を付けて配信する。付けないとブラウザが Last-Modified から勝手に鮮度を推測し、再検証せずに古い JS を使う。ページ遷移では HTML が再検証されるのに JS・CSS だけ古いまま残るため、「新機能を足したのに画面に出ない」という形で現れる（実際に設定画面の予備モデル欄で発生した）。`no-cache` は「保存してよいが使う前に必ず確認せよ」の意味で、変更が無ければ ETag により 304 が返るだけなので転送量は増えない。事務局の PC へ更新版を配るたびにキャッシュを手で消してもらうわけにいかないため、サーバ側で解決している。

**④ 設定画面**

- API キーの保存・削除（保存後は先頭数文字のみ表示。全文は返さない）
- モデル選択（プルダウン + 手入力）
- 再試行回数の設定
- **開発者向け：予備モデル**（折りたたみ。既定は選択なし）

**予備モデルによるフェイルオーバー**：無料枠は 1 モデルあたり 1 日 20 リクエストのため、再試行が入ると 1 モデルではAI モードを完走できない。`fallback_models` に選んだモデルを順に持ち、`RotatingGeminiClient` が枠切れ（429 / RESOURCE_EXHAUSTED）を検出するたびに次のモデルへ移って**同じリクエストを再送**する。枠を使い切ったモデルは以後使わない。

これは開発時に無料枠を足し合わせるための機能である。既定は空で、そのときは従来と完全に同じ挙動になる。事務局の運用では 1 モデルだけを選ぶ。

ラウンドロビンではなくフェイルオーバーにしたのは、確認したいのが「AI が全科目を割り振った時間割」であってモデルの比較ではないためである。チャンクごとに品質の違うモデルが混ざると、何の結果なのか読み解けなくなる。第 1 モデルを使い切るまで使い、あふれた分だけ次へ回す。

枠切れ**以外**の失敗ではモデルを切り替えない。それは一時的な失敗であり、既存の再試行で解決しうるためである。全モデルが枯渇したら `GeminiError` となり、既存の経路でソルバーへ落ちる。どのチャンクをどのモデルが処理したかはログに残す（応答を受け取った**後**に読む。送信前の名前は切り替えが起きると食い違う）。

### 8.2 ログビューア

画面下部の折りたたみパネル。上下ボタンで表示・非表示を切り替える。バックエンドから SSE でリアルタイムに受信し、同時に `logs/YYYY-MM-DD_HHMMSS.log` へ保存する。

記録する内容：

- 各 Stage の開始・終了と所要時間
- チャンク単位の処理内容（対象科目数、学科、開講期）
- Gemini への送信トークン数、応答時間、使用モデル
- 検証で検出した違反の詳細（科目コード、制約 ID、理由）
- 再試行の発生（何回目か、対象科目）
- フォールバックの発動
- 例外のスタックトレース

ログレベルは INFO / WARN / ERROR とし、フロントでフィルタできるようにする。

## 9. Excel 出力

時間割表マトリクス形式（縦 1〜5 限 × 横 月〜金）で出力する。学科 × 学期ごとにシートを分ける。学年での分割は行わない。

| シート |
|---|
| 経営・前期 / 経営・後期 |
| 会計・前期 / 会計・後期 |
| 短大・前期 / 短大・後期 |

1 セルに複数科目が入る場合は改行で併記し、科目名・教員名・年次・科目区分を記載する。短大のクオーター科目はセル内に前①などの表記を添える。集中講義は別シートに一覧として出力する。

## 11. エラー処理

| 事象 | 対応 |
|---|---|
| API キー無効 | ログに記録し、モックモードへの切り替えを促す |
| レート制限 | 指数バックオフで再試行 |
| JSON パース失敗 | 再試行の対象とする |
| タイムアウト | 再試行の対象とする |
| 再試行の上限到達 | Stage 5 のソルバーへフォールバック |
| Excel の列構成が想定外 | MarkItDown 経路にフォールバックし、警告を表示 |

**生成が途中で完全に停止することはない。** どのエラー経路も最終的にソルバーへ到達し、時間割は必ず出力される。

## 13. テスト方針

pytest で以下を検証する。Gemini はモックに差し替えるため、テスト実行に API キーは不要。

| テスト | 内容 |
|---|---|
| `test_constraints.py` | H1〜H10 のそれぞれについて、違反ケースと非違反ケースを 1 組ずつ。開講期間の重なり判定は表 5.4 の全組み合わせを網羅 |
| `test_ingest.py` | 実 Excel の読み込み、氏名正規化（全角空白・異体字）、▲科目の集約、集中講義の除外、警告生成 |
**フロントエンドの検証**：画面側は長く自動検証の外にあり、予備モデル欄が表示されない件と、復元しても結果タブが開かない件を、いずれも実機で初めて見つけた。バックエンドのテストをいくら足してもこの種の不具合は見つからない。

ブラウザ全体を用意する必要はない。`backend/tests/js/dom_stub.js` は `innerHTML` を文字列として持つだけの最小限の DOM で、「何を書き出したか」「どの要素が有効になったか」を確かめるにはこれで足りる。ドライバが結果を JSON で出し、pytest 側が読む。`node` が無い環境では自動的に飛ばす。

テストハーネスを `frontend/` ではなく `backend/tests/` に置いているのは、`make-dist.sh` が `tests` という名前のディレクトリを配布物に見つけるとビルドを中止するためである。

| ドライバ | 対象 |
|---|---|
| `restore_session.js` | セッション復元。どのタブが有効になるか |
| `timetable_render.js` | 学年順の並び、複数コマの移動、未配置科目の配置、HTML エスケープ |
| `settings_models.js` | 予備モデルの表示・保存・並び順、ログパネルの開閉 |

| `test_solver.py` | ソルバーが必ず解を返すこと。制約が厳しすぎて解がない場合に未配置リストを返すこと |
| `test_pipeline.py` | 3 モードそれぞれのパイプラインが完走すること。Gemini が常に違反応答を返す状況でソルバーへフォールバックすること |

検証はすべて実データ（`カリキュラム一覧(整形済み).xlsx`・`教員一覧(整形済み).xlsx`）で行う。事務局が §14 の列を整備済みのため、ダミーデータの生成は不要になった。
