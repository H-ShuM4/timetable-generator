# 大学時間割自動生成システム 設計仕様書

作成日: 2026-08-10

## 1. 目的と背景

大学（経営学科・会計学科）および短期大学部の時間割を、既存の Excel 資産と生成 AI（Google Gemini）を用いて半自動で作成するシステムを開発する。事務局が手作業で行っている曜日・時限の割り当てを支援し、制約違反の見落としを防ぐことを目的とする。

本システムの技術的な要点は「時間割生成という制約充足問題を、LLM 単体で解こうとせず、小さなチャンクへ分割して LLM に配置させ、決定的な検証器で囲い込む」という構成にある。

## 2. スコープ

### 対象

- 経営学科・会計学科・短期大学部の 3 課程
- 曜日：月〜金、時限：1〜5 限
- 開講期：前期・後期（短期大学部の一部はクオーター制：前①・前②・後①・後②）
- 曜日・時限の割り当てのみ

### 対象外

- 教室（講義室・PC 教室）の割り当て。ただし将来追加できるよう、制約層をデータ構造から分離して設計する
- 学生個人の履修登録・時間割
- 「集中」講義（時限 99）の配置。読み込みはするが、時間割グリッドからは除外し、別枠の一覧としてのみ保持する

## 3. 技術スタック

| 層 | 採用技術 | 理由 |
|---|---|---|
| フロントエンド | HTML / CSS / JavaScript（フレームワークなし） | 事務局 PC で追加インストールなく動く。ログの SSE 受信も標準 API で足りる |
| バックエンド | Python 3.14 + FastAPI | ログのリアルタイム配信（SSE）と非同期処理が標準。型定義がそのまま API 仕様になる |
| Excel 読み書き | openpyxl | 既存 Excel が整形済みのため、列を直接構造化して読む方が型が保証され検証も確実 |
| Excel フォールバック | MarkItDown | 想定外の列構成の Excel が投入されたときの経路として併用 |
| 生成 AI | Google Gemini（`google-genai`） | モデル名は設定画面から変更可能 |
| 永続化 | サーバ上の JSON ファイル | DB を立てずに済み、中身を目視してデバッグできる |
| テスト | pytest | Gemini はモックに差し替え、API キーなしで全テストが通る |

### 4.4 既知のデータ課題

| 課題 | 対応 |
|---|---|
| 氏名の空白が全角・半角で揺れる | 正規化して突合 |
| 異体字の揺れ（教員一覧 `降籏 光太郎` / カリキュラム `降旗 光太郎`） | 異体字マッピングテーブルで吸収。それでも一致しない場合のみ警告 |
| 非常勤 59 名中 15 名の出勤可能日が空欄 | 担当科目がある場合のみフロントで入力を促す。担当科目がなければ無視 |
| 合同=○ でも単独のままの科目がある（その教員のコマが片方の学科にしかないゼミなど 14 件） | 正常として扱い、警告は出さない。合同=○ は科目が合同開講であることを示し、ペアは教員単位で成立する |
| 同じ科目・教員・開講期の科目が他学科にあるのに片方だけ合同フラグが付いている | 付け忘れの可能性が高いため `joint_flag_mismatch` として警告する |
| ▲科目は同一授業コードで 2 行 | 1 科目に集約し「必要コマ数 2」として扱う |

## 5. データモデル

### 5.1 Subject（科目）

| フィールド | 型 | 説明 |
|---|---|---|
| `code` | str | 授業コード |
| `name` | str | 科目名称（原文） |
| `base_name` | str | `:会` と `【再】` と先頭 `▲` を除いた正規化名。ゼミ判定・合同ペアリングに使う |
| `department` | Enum | 経営 / 会計 / 短期大学部 |
| `year` | int | 年次配当 |
| `term` | Enum | 前期 / 後期 |
| `quarter` | Enum \| None | 前① / 前② / 後① / 後② |
| `category` | Enum | 必修 / 選択必修 / 選択 |
| `courses` | list[str] | コース・フィールド（複数可） |
| `teacher` | str | 教員氏名（正規化済み） |
| `is_remote` | bool | 遠隔フラグ |
| `joint_id` | str \| None | 合同グループ ID（ペアリングで付与） |
| `slots_required` | int | 必要コマ数。▲科目は 2、通常は 1 |
| `requires_consecutive` | bool | 2 コマ連続が必要か |
| `fixed_slot` | TimeSlot \| None | Excel で入力済みの確定枠 |
| `is_intensive` | bool | 集中講義（時限 99）。グリッド対象外 |
| `is_seminar` | bool | ゼミ科目群に属するか |

### 5.2 Teacher（教員）

| フィールド | 型 | 説明 |
|---|---|---|
| `name` | str | 正規化済み氏名 |
| `kind` | Enum | 専任 / 特任 / 非常勤 / 不明 |
| `research_day` | str \| None | 研究日（専任のみ） |
| `available_days` | set[str] | 出勤可能曜日（特任） |
| `available_slots` | set[TimeSlot] | 出勤可能コマ（非常勤） |

`kind` が `不明`（教員一覧に存在しない）の場合は、警告を出した上で配置する。生成は止めない。

ここでいう「制約なし」は **H5（出勤可能日）と H6（研究日）に限った例外**であり、H1（同一教員の二重予約）と H7（連続コマ）は名簿の有無に関係なく適用する。名簿に載っていない教員も同時刻に二箇所へは行けないためである。判定は `Subject.teacher` の文字列一致で行う。

### 5.3 TimeSlot / Assignment / Timetable

- `TimeSlot`: `day`（月〜金）, `period`（1〜5）
- `Assignment`: `subject_code`, `slots`（TimeSlot のリスト）, `source`（prelock / gemini / solver / manual）
- `Timetable`: Assignment の集合。学科 × 学期でビューを切り出せる

`source` はフロントでの色分け表示に使う。

### 5.4 開講期間の重なり判定

すべての制約は「開講期間が実際に重なる場合のみ衝突」と判定する。この判定は 1 箇所に実装し、全制約から共有する。

| A \ B | 前期 | 前① | 前② | 後期 | 後① | 後② | 通年 |
|---|---|---|---|---|---|---|---|
| 前期 | 重なる | 重なる | 重なる | – | – | – | 重なる |
| 前① | 重なる | 重なる | **重ならない** | – | – | – | 重なる |
| 前② | 重なる | **重ならない** | 重なる | – | – | – | 重なる |
| 後期 | – | – | – | 重なる | 重なる | 重なる | 重なる |
| 後① | – | – | – | 重なる | 重なる | **重ならない** | 重なる |
| 後② | – | – | – | 重なる | **重ならない** | 重なる | 重なる |
| 通年 | 重なる | 重なる | 重なる | 重なる | 重なる | 重なる | 重なる |

前期と後期は常に重ならない。通年は年間を通じて開講されるため、どの期間とも重なる。

現在の実データで開講期間が `通年` なのは短期大学部の `J19901 模擬ブライダルプロジェクト` 1 件のみで、これは集中講義のためグリッド対象外である。それでも判定を正しく実装するのは、将来この科目が通常開講に変わった場合に制約が黙って素通りするのを防ぐためである。

## 6. 制約

すべてハード制約とする。ソフト制約は設けない。

| ID | 制約 | 判定単位 |
|---|---|---|
| H1 | 同一教員が同曜日・同時限に別科目を持たない | 全学科横断。**同じ `joint_id` を持つ科目同士は除外** |
| H2 | 必修同士が衝突しない | 学科 × 年次。**同一科目名の複数クラスは対象外** |
| H3 | 選択必修同士が衝突しない | 学科 × 年次 × コース。異なるコース間は衝突可 |
| H4 | 合同科目のペアは同曜日・同時限 | 合同グループ単位 |
| H5 | 非常勤は出勤可能な曜日・時限のみ／特任は出勤可能な曜日のみ | 教員単位 |
| H6 | 専任の研究日には配置しない | 教員単位 |
| H7 | 同一教員が同一日に 3 コマ以上連続しない | 教員 × 曜日。1 日の合計コマ数に上限は設けない |
| H8 | 短大の遠隔=○ は必ず金曜に配置。大学の金曜配置は自動的にリモート扱い | 科目単位 |
| H9 | Excel で曜日・時限が入力済みの科目は不動 | 科目単位 |
| H10 | ▲科目（`requires_consecutive=true`）は同一日の連続 2 コマに配置 | 科目単位 |

### 補足

- **H1 の除外対象（合同ペア）**：合同科目のペアは 2 行に分かれているが物理的には 1 つの授業であり、担当教員も同一である（実データの合同 107 グループすべてが該当）。H4 が同一コマへの配置を要求する以上、H1 が同一教員として衝突を報告してはならない。両者は直接矛盾するため、H1 は `joint_id` が一致する相手を無視する
- **H2 の除外対象（同一科目の複数クラス）**：`base_name` が一致する必修科目同士は衝突とみなさない。担当教員ごとにクラスが分かれていても学生はそのうち一つを履修するため、同一コマに集約してよい。事務局も従来この方法で過密を解消してきた

  対象はゼミ科目に限らない。日本語リテラシーⅠ（9 クラス）や課題研究Ⅰ（18 クラス）のようなゼミ系だけでなく、英語Ⅰ・情報リテラシーⅠ・商業簿記Ⅰ のように複数クラス開講される通常科目も同じ扱いになる。`base_name` は `:会`・`【再】`・先頭 `▲` を除いた名前なので、`日本語リテラシーⅠ` と `日本語リテラシーⅠ【再】` も同一科目とみなされる

  この規則は必修の必要コマ数を大きく下げる。実データでは 経営 1 年前期 26 科目→18 コマ、会計 1 年前期 24 科目→15 コマ、短期大学部 1 年前期 29 科目→15 コマとなり、いずれも 25 コマに収まる

  なお `Subject.is_seminar` と `config/seminar_subjects.json` は、この一般化により制約判定では使われなくなった。データとしては保持しているが、将来使い道がなければ削除してよい
- **H10 の例外**：`▲プレゼミナール` のみ `requires_consecutive=false`（現行データが火 2 / 木 2 の別日配置のため）。この例外は `config/subject_overrides.json` で管理し、ハードコードしない
- **H7 と H10 の関係**：▲科目の 2 コマ連続は H7 に違反しない（連続 2 コマは許容範囲）
- **H8 の大学側**：現時点では遠隔列を配置制約に使わず、金曜に置かれた科目を自動的にリモートとして扱う。将来「遠隔=○ の科目だけ金曜配置可」へ切り替えられるよう、制約をフラグで切り替え可能にしておく

### 制約層の設計原則

制約の検証は `constraints/validator.py` に集約し、以下の 3 箇所がすべて同じ検証器を呼ぶ。

1. Gemini の応答検証
2. ソルバーの探索中の枝刈り
3. フロントの D&D 編集時のリアルタイム警告

これにより「AI 経由なら通るのに手動編集では弾かれる」といった不整合が原理的に発生しない。教室制約を将来追加する場合も、このモジュールにルールを 1 つ追加するだけで 3 箇所すべてに反映される。

## 7. 生成パイプライン

### Stage 0 — 読み込みと検証

Excel を構造化し、以下を警告一覧として作成する。警告があっても処理は止めない。

- 教員一覧に存在しない担当教員
- 担当科目があるのに出勤可能日が空欄の非常勤
- 合同=○ だがペアが成立しない科目
- コース列が空の選択必修科目
- 曜日・時限が片方だけ入力されている科目

### Stage 1 — 事前ロック（Python のみ、AI に渡さない）

1. `fixed_slot` を持つ科目（H9）をそのまま配置
2. **非常勤**教員の担当科目を、出勤可能コマに決定的に配置する。候補コマ数が少ない教員から順に処理し、H1・H7 を確認しながら確定させる

**特任教員は事前ロックの対象外とする。** 特任の制約は曜日単位（H5）にとどまり時限が定まらないため、Python が機械的に選ぶと恣意的な配置になる。特任の科目は Stage 2〜4 で通常どおり扱い、H5 の曜日制約を適用する。

この段階の結果は以降のステージで**占有済みマップ**として扱われ、Gemini には「そのコマが埋まっている」という事実のみが渡る。トークン削減と、確定枠が AI に動かされないことの保証を兼ねる。

### Stage 2〜4 — Gemini によるチャンク配置

必修 → 選択必修 → 選択 の順に処理する。各段階をさらに分割してリクエストする。

| 段階 | チャンク単位 |
|---|---|
| Stage 2（必修） | 学科 × 開講期 |
| Stage 3（選択必修） | 学科 × コース × 開講期 |
| Stage 4（選択） | 学科 × 開講期 |

1 チャンクあたり数十科目に収まる。各チャンクのループ：

```
プロンプト（対象科目 + 占有済みマップ + 適用制約）
  → Gemini が JSON で配置案を返す
  → validator が検証
  → 違反ゼロなら確定
  → 違反があれば「どの科目がどの制約に違反したか」だけを添えて差し戻す
  → 設定した再試行回数まで繰り返す
```

差し戻し時は**違反した科目のみ**を再配置対象とし、成功済みの配置は再送しない。これにより再試行のトークンが線形に膨らむのを防ぐ。

Gemini の応答は JSON スキーマを指定して受け取り、パース失敗も再試行の対象とする。

### Stage 5 — ソルバーによるフォールバック

再試行を使い切っても未確定の科目を、Python の貪欲探索で埋める。毎回「配置可能なコマ数が最も少ない科目」を選んで確定させる（最小残余値ヒューリスティック）。候補が 1 つも無い科目はその場で未配置として記録し、残りの処理を続ける。

これが「必ず完成する」保証となる。フロントでは `source` により AI 配置とソルバー配置を色分けする。

**バックトラッキングを採用しない理由**：当初はバックトラッキング探索を想定していたが、実測すると 1 ノードあたり 0.21 秒（残り全科目の候補再計算）かかり、443 科目規模では探索が現実的な時間で終わらない。一方、最小残余値ヒューリスティックによる貪欲配置は 90 秒で 443 科目中 435 科目を配置し、制約違反 0 を達成した。未配置の 8 科目は候補が 1 つも無いもので、バックトラッキングでも配置できない。

配置済みの科目を動かせば解が見つかる可能性は残るが、それは Gemini の再試行と事務局の手動編集が担う。ソルバーの役割は「必ず終わり、必ず制約を満たす結果を返す」ことである。

### Stage 6 — 全体検証と保存

全制約を通しで再検証し、結果と残存違反一覧を `data/` 配下の JSON に保存する。

### モードごとの差分

| モード | 挙動 |
|---|---|
| **モックモード** | Stage 2〜4 をスキップし、Stage 5 のソルバーが全科目を配置。API キー未設定時は自動的にこのモードになる |
| **最適化モード** | 上記フルパイプライン |
| **踏襲モード** | Stage 1 の後に前年度時間割を読み込み、組み替え対象外の教員の科目を前年度と同じコマにロックする。組み替え対象のみ Stage 2〜5 に流す |

**踏襲モードの組み替え対象**（自動検出し、フロントでチェックボックスによる追加・除外が可能）：

- 非専任教員（非常勤・特任）の担当科目すべて
- 前年度と今年度で研究日が変わった専任教員の担当科目
- 前年度に存在しない新規科目
- 担当教員が変わった科目

前年度の教員一覧も入力として受け取り、研究日の差分を検出する。

## 8. フロントエンド

### 8.1 画面構成

**① アップロード画面**

Excel を D&D で投入。読み込み後に以下を表示する。

- 科目数（学科別・科目区分別）
- 教員数（区分別）
- クオーター科目数
- 集中講義数
- 警告一覧（Stage 0 で検出したもの）

**② 生成画面**

- モード選択（モック / 最適化 / 踏襲）
- 踏襲モード選択時は組み替え対象一覧を表示し、チェックボックスで調整
- 生成開始ボタン
- 進捗表示（現在の Stage / チャンク）
- ログビューア

**③ 結果画面**

- 学科タブ × 学期タブでグリッド表示（縦 1〜5 限 × 横 月〜金）
- D&D でコマを移動。移動先が制約違反になる場合は即座に赤く警告し、違反理由をツールチップで表示
- `source` による色分け（事前ロック / AI 配置 / ソルバー配置 / 手動編集）
- 未配置科目リスト、集中講義リストをサイドに表示
- Excel 出力ボタン

**④ 設定画面**

- API キーの保存・削除（保存後は先頭数文字のみ表示。全文は返さない）
- モデル選択（プルダウン + 手入力）
- 再試行回数の設定

### 8.2 ログビューア

画面下部の折りたたみパネル。上下ボタンで表示・非表示を切り替える。バックエンドから SSE でリアルタイムに受信し、同時に `logs/YYYY-MM-DD_HHMMSS.log` へ保存する。

記録する内容：

- 各 Stage の開始・終了と所要時間
- チャンク単位の処理内容（対象科目数、学科、開講期）
- Gemini への送信トークン数、応答時間、使用モデル
- 検証で検出した違反の詳細（科目コード、制約 ID、理由）
- 再試行の発生（何回目か、対象科目）
- フォールバックの発動
- 例外のスタックトレース

ログレベルは INFO / WARN / ERROR とし、フロントでフィルタできるようにする。

## 9. Excel 出力

時間割表マトリクス形式（縦 1〜5 限 × 横 月〜金）で出力する。学科 × 学期ごとにシートを分ける。学年での分割は行わない。

| シート |
|---|
| 経営・前期 / 経営・後期 |
| 会計・前期 / 会計・後期 |
| 短大・前期 / 短大・後期 |

1 セルに複数科目が入る場合は改行で併記し、科目名・教員名・年次・科目区分を記載する。短大のクオーター科目はセル内に前①などの表記を添える。集中講義は別シートに一覧として出力する。

## 10. 設定の永続化

| 対象 | 保存先 |
|---|---|
| Gemini API キー | `backend/.env` の `GEMINI_API_KEY` |
| モデル名・再試行回数 | `backend/data/settings.json` |
| 生成結果 | `backend/data/sessions/<session_id>.json` |
| ゼミ科目リスト・科目個別例外 | `backend/config/*.json` |

`.env` は `.gitignore` に登録する。API キーはフロントへ全文を返さない。

## 11. エラー処理

| 事象 | 対応 |
|---|---|
| API キー無効 | ログに記録し、モックモードへの切り替えを促す |
| レート制限 | 指数バックオフで再試行 |
| JSON パース失敗 | 再試行の対象とする |
| タイムアウト | 再試行の対象とする |
| 再試行の上限到達 | Stage 5 のソルバーへフォールバック |
| Excel の列構成が想定外 | MarkItDown 経路にフォールバックし、警告を表示 |

**生成が途中で完全に停止することはない。** どのエラー経路も最終的にソルバーへ到達し、時間割は必ず出力される。

## 13. テスト方針

pytest で以下を検証する。Gemini はモックに差し替えるため、テスト実行に API キーは不要。

| テスト | 内容 |
|---|---|
| `test_constraints.py` | H1〜H10 のそれぞれについて、違反ケースと非違反ケースを 1 組ずつ。開講期間の重なり判定は表 5.4 の全組み合わせを網羅 |
| `test_ingest.py` | 実 Excel の読み込み、氏名正規化（全角空白・異体字）、▲科目の集約、集中講義の除外、警告生成 |
| `test_solver.py` | ソルバーが必ず解を返すこと。制約が厳しすぎて解がない場合に未配置リストを返すこと |
| `test_pipeline.py` | 3 モードそれぞれのパイプラインが完走すること。Gemini が常に違反応答を返す状況でソルバーへフォールバックすること |

合同フラグとコース列は Excel 側が未整理のため、`tests/fixtures/make_dummy_data.py` で現行 Excel からダミー値を生成し、それを用いて検証する。
